# AGENTS.md

Эти правила действуют для всего репозитория `Antiokh/rslive_content`.

## Обязательный порядок чтения

Перед любой работой с содержимым репозитория прочитайте актуальные версии файлов из текущей ветки:

1. `PROJECT_CONTEXT.md` — назначение проекта, источники истины и приоритеты.
2. `README.md` — структура зеркала, frontmatter, сборка и синхронизация.
3. `src/content/docs/CONTENT_INDEX.yml` — проверенные маршруты и контекст перелинковки.
4. `CONTRIBUTING.md` — правила редактирования и проверки статей.
5. `docs/EDITORIAL_POLICY.md` — уровни доказательности, сохранение практической пользы, сроков и пользовательского опыта.
6. `docs/MDX_COMPONENTS.md` — доступные MDX-компоненты и их синтаксис.
7. `docs/CONTRIBUTOR_ATTRIBUTION.md` — правила авторства и Git metadata.
8. `docs/updates/README.md` — обязательное обновление daily/monthly update stack при содержательных изменениях статей.

Не используйте загруженные в ChatGPT, локально сохранённые или процитированные ранее копии этих файлов как актуальный источник. Получайте их заново из GitHub непосредственно перед работой.

## Источники истины

- Актуальный контент и маршруты: ветка `main` репозитория `Antiokh/rslive_content`.
- Реализация Astro, Starlight, автоимпортов и кастомных компонентов: ветка `main` репозитория `Antiokh/rslive.ru`.
- Компоненты проверяйте по:
  - `astro/astro.config.mjs`;
  - `astro/src/components/`;
  - `astro/CUSTOMIZATION_INVENTORY.md`.

При расхождении документации с текущим кодом компонента приоритет имеет текущий код из `Antiokh/rslive.ru`.

## Правила изменения контента

- Перед записью повторно получите текущую версию каждого изменяемого файла и его blob SHA.
- Не перезаписывайте свежие изменения из `main` или чужой ветки.
- Используйте обычный Markdown/MDX и только реально доступные компоненты.
- Не добавляйте локальные `import` для компонентов, которые автоимпортируются глобально.
- Не оставляйте в MDX неподдерживаемую разметку старого движка, кроме специально оговорённых архивных примеров в fenced code blocks.
- Не выдумывайте маршруты, якоря, компоненты, параметры компонентов или таблицы данных.
- Считайте существующие заголовки частью публичной ссылочной структуры статьи: на сгенерированные из них Astro-якоря уже могут вести внутренние и внешние ссылки. При обычной редактуре не удаляйте и не переименовывайте существующие заголовки. Делайте это только в исключительных случаях, когда изменение структуры действительно необходимо; перед таким изменением проверьте ссылки на старый якорь и обновите контролируемые ссылки.
- Для внутренних ссылок используйте абсолютные пути от корня сайта: `/arrival/boravak/`.
- Проверяйте существование маршрута по дереву `src/content/docs` и `CONTENT_INDEX.yml`.
- Якоря добавляйте только после проверки фактического Astro heading ID.
- При создании, удалении, переносе или существенном переименовании страницы обновляйте `src/content/docs/CONTENT_INDEX.yml`.
- При содержательном изменении опубликованной статьи обновляйте соответствующие `docs/updates/daily/YYYY-MM-DD.json`, `docs/updates/daily/YYYY-MM-DD.md` и `docs/updates/monthly/YYYY-MM.md` по правилам `docs/updates/README.md`.
- При переносе страницы проверяйте необходимость 301-редиректа в `Antiokh/rslive.ru: astro/public/_redirects`.

## Редакционный стандарт

- Язык основных русскоязычных статей — русский.
- Тон — энциклопедический, прямой и практичное.
- Формулируйте действия императивно: «проверьте», «подайте», «сохраните».
- Не используйте рекламные обещания, неподтверждённые обобщения и бытовые сроки как гарантированные.
- Разделяйте норму закона, официальную процедуру, практику учреждения и пользовательский опыт.
- Юридические, налоговые, медицинские и административные утверждения подтверждайте актуальными официальными источниками.
- Пользовательские отзывы используйте только как практический контекст и явно обозначайте их статус.
- Не удаляйте полезный практический срок, последовательность действий или пользовательский кейс только из-за отсутствия официального подтверждения. Если информация помогает планировать процедуру и не противоречит установленным фактам, сохраните её, датируйте и явно обозначьте как практику учреждения или пользовательский опыт; отсутствие официального SLA само по себе не является основанием для удаления.
- При фактчеке сначала уточняйте уровень утверждения и формулировку. Удаляйте практическую информацию, когда она неверна, опасна, вводит в заблуждение, бесполезно устарела или не имеет проверяемой практической ценности.
- Сохраняйте сербские термины, когда они помогают найти услугу или норму, и поясняйте их по-русски.
- Используйте числовые сноски `[^1]`, `[^2]`; не применяйте именованные сноски.

Подробные правила сохранения практической информации, сроков и последовательностей находятся в `docs/EDITORIAL_POLICY.md`.

## Компоненты и синтаксис

Критические паттерны нельзя заменять упрощённым текстом без причины:

- предупреждения и примечания — `Aside`;
- последовательности действий — `Steps`;
- группы раскрывающихся блоков — `Accordion` и `AccordionItem`;
- одиночный скрываемый блок — `Spoiler`;
- платёжная квитанция — `UplatnicaGenerator`;
- карта — `MapEmbed`;
- общий iframe — `EmbedFrame`;
- YouTube — `YouTube`;
- включение страницы или раздела — `ContentInclude`;
- фильтруемая таблица — `SmartTable`, `StructTable`, `SupabaseTable` или `SanityTable` в зависимости от источника данных;
- числовые графики — `DataChart`, а графики из Supabase с build-time загрузкой данных — `SupabaseChart`.

Перед использованием компонента сверяйте его текущие props с `Antiokh/rslive.ru`. Не меняйте названия полей `UplatnicaGenerator` и не преобразовывайте квитанцию в картинку или обычную таблицу.

## Git workflow

- По умолчанию создавайте ветку `agent/<краткое-название>` от актуального `main`.
- Не коммитьте напрямую в `main`, если пользователь явно этого не потребовал.
- Один PR должен решать одну связанную задачу.
- По умолчанию создавайте draft PR.
- Не включайте в diff посторонние файлы.
- Перед коммитом проверьте, что `Author` и `Committer` указывают реального человека и используют email, связанный с его аккаунтом GitHub.
- Не указывайте AI-сервисы, модели и агентов в `Author`, `Committer`, `Co-Authored-By`, `Signed-off-by` и других trailers авторства или участия.
- Существенное использование AI-инструмента описывайте в тексте PR, а не в metadata коммита.
- Перед PR сравните ветку с `main` и убедитесь, что она не отстаёт без необходимости.
- В описании PR перечислите:
  - изменённые страницы и правила;
  - причины изменений;
  - использованные источники;
  - выполненные проверки;
  - проверки, которые не удалось выполнить.

## Проверки

Минимально проверьте:

- frontmatter и обязательный `title`;
- парность MDX/JSX-тегов;
- отсутствие неподдерживаемой разметки старого движка;
- отсутствие Markdown autolinks вида `<https://example.com>`;
- корректность внутренних ссылок;
- существование используемых компонентов и их props;
- числовые сноски и определения всех ссылок на сноски;
- отсутствие дублирующих URL в `CONTENT_INDEX.yml`, если он изменён;
- актуальность `docs/updates` для всех содержательных изменений статей в PR.

Полная сборка выполняется в основном репозитории:

```bash
cd astro
npm run build
```

Контентный репозиторий не содержит полного Astro-приложения. Если сборка не запускалась, укажите это в PR без утверждения, что build прошёл.
