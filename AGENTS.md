# AGENTS.md

Эти правила действуют для всего репозитория `Antiokh/rslive_content`.

## Обязательный порядок чтения

Перед любой работой с содержимым репозитория прочитайте актуальные версии файлов из текущей ветки:

1. `PROJECT_CONTEXT.md` — назначение проекта, источники истины и приоритеты.
2. `README.md` — структура зеркала, frontmatter, сборка и синхронизация.
3. `src/content/docs/CONTENT_INDEX.yml` — проверенные маршруты и контекст перелинковки.
4. `CONTRIBUTING.md` — правила редактирования и проверки статей.
5. `docs/EDITORIAL_POLICY.md` — уровни доказательности, сохранение практической пользы, сроков и пользовательского опыта.
6. `docs/MDX_COMPONENTS.md` — доступные MDX-компоненты и их синтаксис.
7. `docs/CONTRIBUTOR_ATTRIBUTION.md` — правила авторства и Git metadata.
8. `docs/updates/README.md` — обязательное обновление daily/monthly update stack при содержательных изменениях статей.

Не используйте загруженные в ChatGPT, локально сохранённые или процитированные ранее копии этих файлов как актуальный источник. Получайте их заново из GitHub непосредственно перед работой.

## Источники истины

- Актуальный контент и маршруты: ветка `main` репозитория `Antiokh/rslive_content`.
- Реализация Astro, Starlight, автоимпортов и кастомных компонентов: ветка `main` репозитория `Antiokh/rslive.ru`.
- Компоненты проверяйте по:
  - `astro/config/mdx-components.config.mjs` — публичный MDX surface и `autoImport` policy;
  - `astro/astro.config.mjs` — wiring integration;
  - `astro/src/components/` — реализация local-компонентов;
  - `astro/CUSTOMIZATION_INVENTORY.md` — архитектурная документация.

При расхождении документации с текущим registry или кодом компонента приоритет имеет текущий код из `Antiokh/rslive.ru`.

## Правила изменения контента

- Перед записью повторно получите текущую версию каждого изменяемого файла и его blob SHA.
- Не перезаписывайте свежие изменения из `main` или чужой ветки.
- Используйте обычный Markdown/MDX и только реально доступные компоненты.
- Не добавляйте локальные `import` для компонентов, у которых canonical registry задаёт `autoImport: true`.
- Не оставляйте в MDX неподдерживаемую разметку старого движка, кроме специально оговорённых архивных примеров в fenced code blocks.
- Не выдумывайте маршруты, якоря, компоненты, параметры компонентов или таблицы данных.
- Считайте существующие заголовки частью публичной ссылочной структуры статьи: на сгенерированные из них Astro-якоря уже могут вести внутренние и внешние ссылки. При обычной редактуре не удаляйте и не переименовывайте существующие заголовки. Делайте это только в исключительных случаях, когда изменение структуры действительно необходимо; перед таким изменением проверьте ссылки на старый якорь и обновите контролируемые ссылки.
- Для внутренних ссылок используйте абсолютные пути от корня сайта: `/arrival/boravak/`.
- Проверяйте существование маршрута по дереву `src/content/docs` и `CONTENT_INDEX.yml`.
- Якоря добавляйте только после проверки фактического Astro heading ID.
- При создании, удалении, переносе или существенном переименовании страницы обновляйте `src/content/docs/CONTENT_INDEX.yml`.
- При содержательном изменении опубликованной статьи обновляйте соответствующие `docs/updates/daily/YYYY-MM-DD.json`, `docs/updates/daily/YYYY-MM-DD.md` и `docs/updates/monthly/YYYY-MM.md` по правилам `docs/updates/README.md`.
- При переносе страницы проверяйте необходимость 301-редиректа в `Antiokh/rslive.ru: astro/public/_redirects`.


### Frontmatter `navigator`

- `navigator` — опциональная классификация статьи для персонального навигатора. Канонический синтаксис и словарь тегов находятся в `docs/RELOCATION_WIZARD.md`.
- Не используйте поисковый `keywords` вместо `navigator`: это разные поля с разным назначением.
- Короткая форма одной фазы: `now: [traveling, pets]`. Теги внутри квадратных скобок соединяются по **И**.
- Несколько вариантов одной фазы задавайте списком массивов; варианты соединяются по **ИЛИ**.
- Не придумывайте новые navigator-теги в статье. Сначала добавьте семантику тега в движок и синхронно обновите документацию и линтер.
- Единственный источник правил показа статьи — её `navigator` frontmatter. Не создавайте отдельные JSON-матрицы, ручные `href`, `title`, `summary`, `reason`, `progressId` или order-списки для навигатора.

## Редакционный стандарт

- Язык основных русскоязычных статей — русский.
- Тон — энциклопедический, прямой и практический.
- Формулируйте действия императивно: «проверьте», «подайте», «сохраните».
- Не используйте рекламные обещания, неподтверждённые обобщения и бытовые сроки как гарантированные.
- Разделяйте норму закона, официальную процедуру, практику учреждения и пользовательский опыт.
- Юридические, налоговые, медицинские и административные утверждения подтверждайте актуальными официальными источниками.
- Пользовательские отзывы используйте только как практический контекст и явно обозначайте их статус.
- Не удаляйте полезный практический срок, последовательность действий или пользовательский кейс только из-за отсутствия официального подтверждения. Если информация помогает планировать процедуру и не противоречит установленным фактам, сохраните её, датируйте и явно обозначьте как практику учреждения или пользовательский опыт; отсутствие официального SLA само по себе не является основанием для удаления.
- При фактчеке сначала уточняйте уровень утверждения и формулировку. Удаляйте практическую информацию, когда она неверна, опасна, вводит в заблуждение, бесполезно устарела или не имеет проверяемой практической ценности.
- Сохраняйте сербские термины, когда они помогают найти услугу или норму, и поясняйте их по-русски.
- Используйте числовые сноски `[^1]`, `[^2]`; не применяйте именованные сноски.

Подробные правила сохранения практической информации, сроков и последовательностей находятся в `docs/EDITORIAL_POLICY.md`.

## Компоненты и синтаксис

Критические паттерны нельзя заменять упрощённым текстом без причины:

- предупреждения и примечания — `Aside`;
- последовательности действий — `Steps`;
- группы раскрывающихся блоков — `Accordion` и `AccordionItem`;
- одиночный скрываемый блок — `Spoiler`;
- платёжная квитанция — `UplatnicaGenerator`;
- карта — `MapEmbed`;
- общий iframe — `EmbedFrame`;
- YouTube — `YouTube`;
- включение страницы или раздела — `ContentInclude`;
- фильтруемая таблица — `SmartTable`, `StructTable`, `SupabaseTable` или `SanityTable` в зависимости от источника данных;
- числовые графики — `DataChart`, а графики из Supabase с build-time загрузкой данных — `SupabaseChart`.

Перед использованием компонента сверяйте его текущие props с `Antiokh/rslive.ru`. Не меняйте названия полей `UplatnicaGenerator` и не преобразовывайте квитанцию в картинку или обычную таблицу.

## Обязательный проектный трекер

GitHub Project **RSLive** (`https://github.com/users/Antiokh/projects/1`) — обязательный трекер для работы в `Antiokh/rslive_content` и `Antiokh/rslive.ru`.

- Перед началом задачи проверьте связанные Issue и PR в проекте, а не только в списках конкретного репозитория.
- Любой Issue или PR, относящийся к работе RSLive, должен быть добавлен в этот проект. Это относится и к уже существующим карточкам, если они ещё не попали в проект.
- При создании нового Issue или PR сразу добавьте его в проект.
- Поле `Status` в проекте должно отражать фактическое состояние работы. Используйте уже существующие значения проекта; не создавайте, не переименовывайте и не удаляйте статусы или поля без прямой просьбы пользователя.
- Обновляйте `Status`, когда меняется состояние работы: начало выполнения, блокировка, перевод draft PR в ready for review, завершение, merge или закрытие без реализации.
- Состояние Issue/PR в репозитории (`open`, `closed`, `draft`, `merged`) не заменяет поле `Status` проектного трекера.
- Перед завершением задачи повторно проверьте, что все затронутые Issue/PR присутствуют в проекте и их `Status` актуален.

### Граница согласованной работы и предложения

- Реализуйте только изменения, которые пользователь прямо одобрил или которые однозначно входят в согласованный scope текущей задачи или Issue.
- Если в ходе работы обнаружена полезная идея, рефакторинг, архитектурное улучшение, изменение security/policy/workflow/dependencies или иное расширение scope, которое пользователь отдельно не одобрил, не внедряйте его «заодно».
- Такое предложение оформите отдельным Issue в подходящем репозитории. Кратко опишите наблюдение, причину, ожидаемую пользу, риски или компромиссы и предлагаемый способ реализации. Используйте только уже существующие релевантные labels; новые labels без прямой просьбы не создавайте. Assignee по умолчанию не назначайте, если ответственный явно не определён.
- Добавьте такой Issue в Project **RSLive** и установите `Status = To Do`. Создание Issue фиксирует предложение на рассмотрение и не означает одобрение реализации.
- Пока пользователь явно не одобрил предложение, не создавайте для него ветку или PR и не меняйте контент, код, конфигурацию, workflows, secrets, архитектуру или политику проекта ради этого предложения.
- Исключение — минимальные изменения, без которых невозможно корректно завершить уже согласованную задачу или пройти существующие обязательные проверки. Если для решения требуется заметно расширить scope, зафиксируйте это отдельным Issue вместо самостоятельного расширения работы.
- Если Projects API недоступен агенту, всё равно создайте Issue и поддержите его нативную metadata; явно укажите, что membership или `Status = To Do` в Project не удалось проверить или выставить. Недоступность Project не является разрешением начать реализацию.

### Контракт GitHub metadata

Project рассматривается как представление над нативными данными GitHub. Для системных полей источником истины является сам Issue/PR и его связи, а не ячейка в Project. Поэтому отсутствие у агента прямого Projects API не освобождает от обновления доступной GitHub metadata.

- `Assignees`, `Labels`, `Milestone` и `Repository` поддерживайте на самом Issue/PR: GitHub автоматически отражает их в Project. Не пытайтесь дублировать эти значения в отдельные custom fields.
- Сохраняйте существующие релевантные labels и используйте уже существующие labels репозитория для типа и области работы. Не создавайте новые labels без необходимости или прямой просьбы. Если PR реализует Issue, перенесите на PR релевантные тематические labels, когда это соответствует принятой схеме репозитория.
- Assignee должен отражать реального ответственного. Не назначайте пользователя, бота или агента без основания в задаче, Issue или действующей политике репозитория; при смене ответственности обновляйте assignee на исходной сущности.
- Если работа ведётся по существующему Issue, связывайте реализацию через нативный `Development`: по возможности создавайте linked branch от Issue, а после открытия PR обеспечьте нативную связь Issue ↔ PR. Для PR, который полностью закрывает Issue, используйте supported closing keyword; для частичной или вспомогательной работы не используйте closing keyword только ради связи.
- `Linked pull requests` и `Reviewers` должны формироваться из реальной GitHub-связи и review requests. Не имитируйте их текстовыми custom fields.
- Для иерархии и зависимостей используйте нативные relationships GitHub (`parent/sub-issue`, `blocked by/blocking`, а также доступные `Tracks/Tracked by`) вместо дублирования связей только в тексте. Если инструмент агента не умеет создать конкретный тип relationship, сохраните явную ссылку в Issue/PR и укажите это ограничение в результате.
- Ветка `agent/*`, связанный Issue и PR должны описывать одну и ту же единицу работы. Само совпадение имени ветки с номером Issue не считается нативной связью.
- Перед завершением работы перепроверьте нативную metadata затронутых Issue/PR: assignees, labels, milestone при наличии, linked PR/Issue, reviewers и relationships. Эти данные должны оставаться корректными независимо от доступности Project.
- `Status` — отдельное project field и не выводится из labels/assignees. Для PR `rslive_content` его синхронизирует repository workflow; при прямом доступе к Project агент также обязан поддерживать его актуальным.
- Если Projects API недоступен, продолжайте обновлять нативную metadata и явно сообщайте только о том, что нельзя было проверить или изменить непосредственно в Project (например, membership или custom `Status`). Не утверждайте, что такие project-only поля обновлены.

## Git workflow

- По умолчанию создавайте ветку `agent/<краткое-название>` от актуального `main`.
- Не коммитьте напрямую в `main`, если пользователь явно этого не потребовал.
- Один PR должен решать одну связанную задачу.
- По умолчанию создавайте draft PR.
- Не включайте в diff посторонние файлы.
- Перед коммитом проверьте, что `Author` и `Committer` указывают реального человека и используют email, связанный с его аккаунтом GitHub.
- Не указывайте AI-сервисы, модели и агентов в `Author`, `Committer`, `Co-Authored-By`, `Signed-off-by` и других trailers авторства или участия.
- Существенное использование AI-инструмента описывайте в тексте PR, а не в metadata коммита.
- Перед PR сравните ветку с `main` и убедитесь, что она не отстаёт без необходимости.
- В описании PR перечислите:
  - изменённые страницы и правила;
  - причины изменений;
  - использованные источники;
  - выполненные проверки;
  - проверки, которые не удалось выполнить.

## Проверки

Минимально проверьте:

- frontmatter и обязательный `title`;
- парность MDX/JSX-тегов;
- отсутствие неподдерживаемой разметки старого движка;
- отсутствие Markdown autolinks вида `<https://example.com>`;
- корректность внутренних ссылок;
- существование используемых компонентов и их props;
- числовые сноски и определения всех ссылок на сноски;
- отсутствие дублирующих URL в `CONTENT_INDEX.yml`, если он изменён;
- актуальность `docs/updates` для всех содержательных изменений статей в PR.

Полная сборка выполняется в основном репозитории:

```bash
cd astro
npm run build
```

Контентный репозиторий не содержит полного Astro-приложения. Если сборка не запускалась, укажите это в PR без утверждения, что build прошёл.
