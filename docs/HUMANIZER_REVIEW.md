# Отзыв редколлегии

Для изменений русскоязычных MDX-страниц репозиторий запускает редакторскую проверку на базе [`Antiokh/humanizer_russian`](https://github.com/Antiokh/humanizer_russian). В GitHub она называется **«Отзыв редколлегии»**.

## Что видит автор PR

Комментарий устроен как отзыв восьми редакторов, а не как технический отчёт:

1. 📚 **Русский язык** — норма, употребление, пунктуация, кальки и другие общие языковые сигналы;
2. 💬 **Живой русский** — естественность, повторы и связность текста;
3. 🪶 **Корней Чуковский** — формализованные правила по книге «Живой как жизнь»;
4. ✒️ **Нора Галь** — формализованные правила по книге «Слово живое и мертвое»;
5. ✂️ **Максим Ильяхов и Людмила Сарычева** — формализованные правила «Пиши, сокращай» и зарегистрированных дополнительных материалов;
6. 🌍 **Линн Виссон** — русско-английская интерференция и естественность русской речи;
7. 📐 **Д. Э. Розенталь** — культура речи, норма и литературная правка;
8. 🔎 **И. Б. Голуб** — стилистика и культура речи.

Все восемь редакторов показываются всегда. Если конкретная библиотека не нашла новых замечаний, рядом выводится «Замечаний нет».

У замечания основным текстом показываются:

- понятное русское название;
- проверяемый фрагмент;
- русскоязычное объяснение;
- путь к файлу, если PR меняет несколько русских страниц.

Машинные значения вроде `rule_id`, `phenomenon_id`, `SINGLE_REVIEW`, `REVIEW`, `CHANGE` и внутренних классов не выводятся как основной отзыв. Они сохраняются под раскрываемым блоком **«🔧 Технические сведения о проверке»** для диагностики.

## Зафиксированная версия

Workflow использует полный SHA `humanizer_russian`, а не плавающую ветку `main`. Одинаковый `HUMANIZER_SHA` должен быть указан в:

- `.github/workflows/humanizer-russian-review.yml`;
- `.github/workflows/humanizer-input-contract.yml`.

Текущая версия: `81af17bcb18ae9364a9f94f4e2f849a68d3b1eee`. Это версия после русификации человекочитаемых сообщений Humanizer.

При обновлении pin меняйте оба workflow одновременно и запускайте контрактную проверку.

## Что именно проверяется

Если MDX-файл изменён, редколлегия получает полную новую версию статьи и, отдельно, полную базовую версию.

Из YAML используются только редакторские поля:

- `title`;
- `description`, если оно есть.

К ним добавляется читательский текст из основного MDX. Остальные служебные поля YAML (`keywords`, `ogSticker`, `sidebar`, `live` и другие) в редакторскую проверку не передаются.

Перед отправкой в Humanizer адаптер маскирует технический MDX/JSX-синтаксис, но сохраняет статический текст, который реально выводят компоненты. Обычный дочерний текст компонента остаётся в проверке. Для props действует явный контракт: общие текстовые поля вроде `title`, `label`, `caption`, `description` и `note` сохраняются; для структурных props отдельно извлекаются, например, `SmartTable.columns[].label`, видимые значения `SmartTable.rows`, текстовые данные `DataChart` и `MapEmbed.point.title/description`. Служебные props вроде `regions`, `id`, URL, ключей колонок и других настроек не считаются прозой.

Из выражений адаптер не исполняет JavaScript: он сохраняет только статические строковые литералы с кириллицей в разрешённых читательских полях. Это сознательная граница CI-проверки.

Это позволяет анализировать текст в контексте статьи, не смешивая его с конфигурацией компонентов и при этом не теряя текст, который компонент получает через props.

## Какие замечания попадают в PR

Полные базовая и новая версии проверяются отдельно. Затем адаптер вычитает находки, которые уже существовали в базовой версии.

Поэтому:

- контекст проверки — вся статья;
- комментарий PR — только новые замечания текущего изменения;
- старый редакционный долг не приписывается автору текущего PR.

Одинаковая находка определяется по библиотеке, правилу, явлению, внутреннему классу, уровню автоматизации, решению и нормализованному фрагменту.

Если несколько редакторов отмечают один и тот же фрагмент, их замечания показываются отдельно в разделах соответствующих редакторов. Внутреннее объединение редколлегии и машинные решения сохраняются в техническом блоке.

Чтобы комментарий не становился чрезмерно длинным, основной текст показывает не более 40 новых находок. Общее количество при этом считается по полному набору.

## Что проверка не делает

- Не определяет авторство текста и не выдаёт «вероятность ИИ».
- Не заменяет ручную редактуру.
- Не превращает совет конкретного автора автоматически в норму русского языка.
- Не запускает модельные карточки и LLM-семантическую правку в GitHub Actions.
- Не блокирует merge сама по себе.
- Не проверяет `/en/`, `/sr/` и файлы без достаточного количества русского текста.
- Не включает дополнительные источники со статусом `PROJECT` в автоматическом режиме.

## Самопроверка интеграции

`.github/workflows/humanizer-input-contract.yml` выполняет:

```bash
python3 .github/scripts/humanizer_pr_review.py \
  --humanizer-root /tmp/humanizer_russian \
  --self-test
```

Проверка подтверждает, что:

1. используется режим `editorial_board`;
2. загружен стиль `rslive_content`;
3. активны восемь библиотек;
4. проверяется полная статья;
5. сырой служебный YAML исключается;
6. контрольное правило `ILY-M01` срабатывает в `title` и `description`, но не в скрытом служебном поле;
7. технические MDX/JSX-теги и служебные props исключаются;
8. видимые текстовые props компонентов остаются в проверке;
9. `SmartTable` сохраняет заголовки колонок и видимые строковые значения строк, но не технические ключи;
10. `UplatnicaGenerator` сохраняет текст плательщика, назначения и получателя;
11. обычный дочерний текст компонентов остаётся в проверке;
12. основной текст статьи входит в проверку;
13. публичное название равно «Отзыв редколлегии»;
14. в публичном слое зарегистрированы восемь редакторов;
15. машинный статус `REVIEW` не является частью человекочитаемого представления замечания.

Если контракт Humanizer или подготовка MDX изменится несовместимо, этот workflow должен упасть до публикации нового формата комментария.

## Безопасность PR

Основной workflow работает на событии `pull_request`.

Исполняемый `.github/scripts/humanizer_pr_review.py` для комментария берётся из **base SHA**. Предложенная ветка используется как источник изменённого контента, но не может подменить код проверки, который выполняется с правом записи комментария.

Отдельный workflow контракта имеет только `contents: read` и проверяет предложенную версию адаптера без права публикации комментариев.

Комментарий создаётся только для PR внутри этого репозитория и не публикуется для `dependabot[bot]`.

Маркер `<!-- humanizer-russian-review -->` сохраняется. Поэтому после изменения формата workflow обновляет существующий комментарий, а не создаёт новый.
