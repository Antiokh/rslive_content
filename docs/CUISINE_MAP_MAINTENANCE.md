# Агентский регламент: карта национальных кухонь Белграда

Обязателен для всех агентов, которые исследуют, добавляют, исправляют и перепроверяют рестораны. Не является пользовательской статьёй. Очередь: [CUISINE_MAP_REVIEW_QUEUE.md](CUISINE_MAP_REVIEW_QUEUE.md). История большого расширения: [PR #461](https://github.com/Antiokh/rslive_content/pull/461), [Issue #462](https://github.com/Antiokh/rslive_content/issues/462).

## Источники истины и область работы

- Прочитать актуальные `AGENTS.md`, `PROJECT_CONTEXT.md`, `map-data/README.md`, `docs/EDITORIAL_POLICY.md` и статью `src/content/docs/map/cuisine/index.mdx`. Три файла ниже получать из GitHub непосредственно перед работой; не использовать старый ответ ИИ или копию как источник истины.
- `map-data/packs/poi/belgrade-world-restaurants.geojson` — физические точки, стабильные ID, категория и кухня, RU-описание, координаты и источники. `belgrade-world-restaurants.en.json` и `.sr.json` — переводы по тем же ID. Сербский — кириллица. MDX-списки PlanPlus — кандидаты, не доказательство существования; сохранение ссылки в списке не означает наличие точки.
- Движок и доступные markerIcon — текущий код Antiokh/rslive.ru, main. Не выдумывать новый флаг. Родизио использует зарегистрированный food, пока нет flag-br. Не менять формат GeoJSON без проверки движка.

## Решение о публикации

| Статус | Действие |
|---|---|
| Действует, адрес/кухня/координаты доказаны | Добавить или обновить точку и все переводы. |
| Временно закрыт | Не публиковать, существующую точку снять после проверки; сохранить ID/историю и вернуть при подтверждении открытия. |
| Предположительно закрыт | Не публиковать, сохранить в списке проверки закрытия; не называть окончательно закрытым. |
| Окончательно закрыт | Не публиковать; зафиксировать доказательство и историю. |
| Недостаточно подтверждений | Не публиковать; сохранить в очереди, указать конкретный недостающий факт. |
| Дубликат | Один ID для одной физической точки; разные филиалы — разные ID. |
| Переименование/переезд/новый арендатор | Сохранить ID только при доказанной непрерывности бизнеса; новый бизнес — новый ID. Старый адрес не переносить автоматически. |
| Не соответствует кухне | Исключить из данной категории, не утверждать закрытие. |

Существующая карта включает действующие заведения с подтверждённой доставкой и/или самовывозом, для которых наличие зала иногда не доказано. Не выдавать такие точки за подтверждённые залы; явно оговаривать это во всех языках. Не публиковать неподтверждённую кухню доставки только из регистрационной карточки. Временное закрытие платформы доставки не доказывает закрытие ресторана.

## Как проверять

1. Установить идентичность: название, варианты написания, конкретный филиал, улица/номер/этаж, телефон, сайт, соцсети; сравнить с текущими точками. Поиск по адресу и телефону обязателен при конфликте. Не считать совпадение номера дома доказательством одного помещения.
2. Проверить текущую работу: сайт владельца/ТЦ, актуальное меню или доступная доставка, датированный отзыв о фактическом посещении, официальное объявление об открытии/закрытии. Предпочтительны два независимых свидетельства, одно первичное или свежий факт работы. При отсутствии официального сайта оценивать качество альтернатив. Статический справочник, дата индексации, регистрация/финансовый статус компании, повторные языковые версии одного агрегатора и автоматически показанные часы не подтверждают работу самостоятельно. Снимок поиска при недоступной странице отмечать отдельно; не выдавать за прочитанный оригинал. При конфликте не угадывать.
3. Проверить национальную специализацию по меню и самоописанию. Не приписывать кухню по национальности владельца; смешанную кухню обозначать честно. Не копировать рекламный текст, оценки и быстро меняющиеся цены.
4. Координаты: предпочесть каноническую Google Maps place URL из источника, затем геометку конкретного Wolt-филиала, именованный OSM-объект или иной адресный источник. Из Google URL брать координаты места, не центра viewport; порядок GeoJSON [longitude, latitude]. При использовании здания/ТЦ как fallback явно обозначить приблизительность. Общий pin ТЦ может быть у разных арендаторов; не смещать искусственно. Сверять расположение и адрес, не изобретать координаты. По возможности визуально проверить вход.
5. Записать прямые ссылки, даты фактических событий и проверки, конфликтующие данные и основание решения. В `properties.coordinateSources` вести существующую схему sourceId/snapshotAt/note; в каждой точке — соответствующий sourceId, provenanceUrl (официальный сайт предпочтителен), mapUrl (канонический URL, координаты как fallback). Не переписывать всю историю датой новой проверки. Устаревшие URL и неподтверждённые входы отмечать отдельно.
6. В очереди хранить неразрешённые факты, а не выдуманные статусы. При повторном обходе искать действительно новые данные; если онлайн-источники исчерпаны, передать редактору список для звонков, визитов или независимого ИИ. Не заявлять, что звонок/визит был сделан, если его не было.

## Изменения и проверки

- Получить main, ветку, PR и SHA каждого файла перед записью. Атомарно изменить GeoJSON и оба языковых файла; при добавлении перевода не удалять старый ID. Сохранять читаемое форматирование, одну запись feature на строку. Обновлять snapshotAt/sourceSnapshotAt согласованно при изменении карты. Если есть sibling .geojson.gz, обновить одновременно по README; не создавать без необходимости.
- Запустить `node scripts/check-map-data.mjs` (CI «Карты»). Проверяются уникальные IDs, nonempty RU/EN/SR, точное совпадение ключей, Point/конечные координаты, metadata источников, отсутствие устаревшего gzip. Дополнительно проверить дубликаты имён, URL и координат, разумные границы Белграда (грубый ориентир lon 20.18–20.68, lat 44.68–44.97; исключения проверять, не отсекать автоматически), соответствие кухни/иконки engine registry. Старые записи без mapUrl имеют координаты и могут использовать штатный fallback; исправлять при наличии проверенного URL, не подделывать.
- Сравнить с main и предыдущим SHA: все не относящиеся к задаче точки, переводы, источники и документы сохранены. При конкурирующем изменении не затирать main. Проверить результаты CI конкретного финального SHA. Не заявлять о пройденном Astro build или визуальной проверке без запуска.
- В PR/Issue отразить число добавленных, исправленных, снятых, отложенных, список источников, ограничения. Не считать обновление/исключение добавлением. Merge только по явной просьбе редактора и после проверок; отслеживать downstream sync отдельно. Сохранять рабочую очередь в docs, а не только в длинном Issue.

## Регулярное обслуживание

Рекомендуемый порядок: сначала сигналы о закрытии или переезде (жалоба читателя, закрытая карта, исчезновение из каталога ТЦ), затем очередь и новые филиалы, затем ротационная проверка существующих точек по районам/кухням. Для каждой проверенной точки сохранять дату, статус и источник в текущих метаданных или отчёте. Не менять массово даты для объектов, которые не проверялись. Публикация заведения не гарантирует, что оно открыто в момент визита. При отсутствии новых доказательств сохранять LKG, не создавать повторные задачи на те же сведения.
