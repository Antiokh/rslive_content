# Автоматический `CONTENT_INDEX.yml`

`src/content/docs/CONTENT_INDEX.yml` — производный семантический индекс страниц RSLive для редакторов, ИИ и инструментов перелинковки. Его **не редактируют вручную**.

Источники истины:

- маршруты MD/MDX-страниц — дерево `src/content/docs/**`;
- название, описание и поисковая семантика — frontmatter самой страницы;
- редкие публичные маршруты движка без MD/MDX — `tools/content-quality/content-index-static-pages.yml`.

## Что генерируется автоматически

Для каждой MD/MDX-страницы генератор получает:

- `url` — из пути файла;
- `locale` — из `/en/` и `/sr/`;
- `title` — из `title`;
- `description` — из `description`, если поле есть;
- `keywords` — из `keywords`, если поле есть;
- `tags` — из `keywords`, стабильных тегов раздела и опционального `linking.tags`;
- `aliases` — из опционального `linking.aliases`;
- `link_when` — из опционального `linking.when` плюс базовый контекст, автоматически построенный из `title` и `description`;
- `anchors` — пока пустой список: конкретный heading ID проверяют по статье и фактическому Astro output.

Теги раздела нужны, чтобы не дублировать одинаковые служебные понятия во frontmatter каждой статьи. Например, страницы `/arrival/**` автоматически получают контекст «переезд» и «первые шаги», `/gov/**` — «госуслуги» и «документы», `/blog/**` — «блог».

## Frontmatter `linking`

`linking` нужен только для семантики, которую нельзя нормально вывести из `title`, `description`, `keywords` и раздела страницы.

```yaml
linking:
  tags:
    - национальная кухня
  aliases:
    - карта национальных кухонь Белграда
    - рестораны разных кухонь Белграда
  when:
    - ищешь ресторан определённой национальной кухни в Белграде
    - нужна карта заведений по кухням разных стран
```

`tags` — дополнительные смысловые понятия, которые нужны семантическому индексу, но не обязательно являются SEO-keywords.

`aliases` — дополнительные названия, термины и формулировки запроса.

`when` — специальные пользовательские сценарии, при которых ссылка на страницу особенно уместна.

Все три поля опциональны. Если `linking` присутствует, в нём должен быть хотя бы один непустой массив. Пустые строки и дубли внутри массива запрещены Astro schema и генератором.

Не переносите в `linking` фразы, уже нормально выраженные основным frontmatter. Это поле предназначено для исключений, а не для второй копии SEO metadata.

## Публичные маршруты без MDX

Некоторые legacy/runtime-страницы принадлежат движку и не имеют файла в `src/content/docs/**`. Они перечислены отдельно в:

```text
tools/content-quality/content-index-static-pages.yml
```

Этот manifest должен оставаться маленьким. Не используйте его для обычных статей: если существует MD/MDX-файл, маршрут и семантика должны выводиться из него.

Перед добавлением static route проверьте его фактическое существование в `Antiokh/rslive.ru`.

## Генерация

Канонический генератор:

```text
tools/content-quality/generate-content-index.mjs
```

После установки зависимостей инструмента:

```bash
npm install --prefix tools/content-quality --package-lock=false --ignore-scripts --no-audit --no-fund
node tools/content-quality/generate-content-index.mjs
```

Проверка committed-файла без записи:

```bash
node tools/content-quality/generate-content-index.mjs --check
```

## Проверка миграции со старого индекса

Первый переход с ручного индекса использует:

```bash
node tools/content-quality/generate-content-index.mjs --audit-legacy
```

Проверка сравнивает legacy routes и нормализованные семантические понятия со страницами, которые построит новый генератор. Морфологические формы и повторяющиеся теги разделов нормализуются, чтобы не считать `банк` и `банки` разными потерями смысла.

Если после автоматической генерации у статьи теряется действительно полезный тег, синоним или сценарий, дополните frontmatter этой статьи через `linking` и повторите аудит. Цель миграции — не механически скопировать старый YAML, а сохранить полезную семантику без ручного дублирования.

## CI и pull request

Feature-ветки не должны вручную обновлять `CONTENT_INDEX.yml`.

`content-quality` строит временный индекс прямо в checkout проверяемого PR, поэтому линтер видит маршруты и metadata того же состояния дерева. Временная проекция не пушится в feature-ветку.

После изменения `main` workflow `Индекс контента`:

1. строит индекс из актуального дерева и frontmatter;
2. проверяет, что `main` не продвинулся за время генерации;
3. при наличии diff делает отдельный generated commit с `[skip content-sync]`.

Маркер нужен, чтобы этот служебный commit не запускал вторую публикацию сайта.

## Синхронизация с `rslive.ru`

Публикационный workflow `notify-rslive-ru.yml` **сам строит индекс из того content SHA, который собирается синхронизировать**, до `rsync` в движок.

Поэтому возможная задержка отдельного generated commit в `rslive_content/main` не может отправить в `rslive.ru` устаревший индекс: runtime-зеркало получает индекс, построенный из того же дерева, что и статьи публикации.

## Правило для редакторов и агентов

При создании, переносе или изменении страницы:

1. меняйте MD/MDX-файл и его frontmatter;
2. не редактируйте `CONTENT_INDEX.yml` вручную;
3. добавляйте `linking` только для дополнительного семантического контекста;
4. существование маршрута проверяйте прежде всего по дереву `src/content/docs/**`;
5. для якоря открывайте статью и проверяйте фактический Astro heading ID.
