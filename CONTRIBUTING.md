# CONTRIBUTING.md

## Перед началом

Прочитайте `AGENTS.md`, `PROJECT_CONTEXT.md`, `README.md`, `src/content/docs/CONTENT_INDEX.yml` и `docs/MDX_COMPONENTS.md`.

Получите актуальную версию статьи из GitHub непосредственно перед редактированием. Не работайте по копии из истории чата или старому вложению.

## Структура статьи

Каждая страница обычно находится в папке с `index.mdx`:

```text
src/content/docs/move/visa/index.mdx -> /move/visa/
```

Минимальный frontmatter:

```mdx
---
title: "Название статьи"
description: "Краткое описание для поисковой выдачи и превью."
keywords: ["ключевая фраза", "другая фраза"]
---
```

Правила:

- `title` обязателен по схеме.
- `description` обязателен по редакционному стандарту для новых и существенно переписанных публичных статей; старые страницы могут временно не иметь его.
- `keywords` должны отражать реальные поисковые формулировки, а не повторять одно слово.
- `source` сохраняйте для мигрированных страниц, если он уже есть.
- Не добавляйте `source` новым страницам без реального исторического источника.
- Для меню используйте `sidebar.label`, `sidebar.order` и `sidebar.hidden` только после проверки логики в `Antiokh/rslive.ru: astro/astro.config.mjs`.

## Рекомендуемая структура материала

Используйте структуру по задаче, а не формальный шаблон. Для процедурной статьи обычно подходят:

```mdx
Короткое вступление: кому нужна статья и какой вопрос она решает.

## Кратко

Основные выводы и ограничения.

## Кто может воспользоваться

Условия и исключения.

## Порядок действий

<Steps>
1. Первый шаг.
2. Второй шаг.
3. Третий шаг.
</Steps>

## Документы

Список документов с оговорками по основанию.

## Сроки и расходы

Только подтверждённые данные с датой проверки.

## Что делать при отказе или проблеме

Практический порядок действий.

## См. также

Внутренние ссылки на связанные статьи.

[^1]: Официальный источник.
```

Не создавайте разделы без содержательной необходимости.

## TOV и терминология

- Пишите энциклопедично, прямо и без рекламы.
- Давайте читателю действие: «проверьте», «получите», «подайте», «сохраните».
- Не обещайте одобрение, срок или результат, если они зависят от органа или организации.
- Поясняйте различия между законом, официальной инструкцией и практикой применения.
- Используйте терминологию последовательно: `privremeni boravak` — временное пребывание / РВП; `stalno nastanjenje` — постоянное проживание / ПМЖ. Не называйте оба статуса общим «ВНЖ» без пояснения, если это стирает юридически значимое различие.
- При первом употреблении полезного сербского термина дайте русский эквивалент.
- Не используйте разговорные отзывы как подтверждение нормы.

## Источники и сноски

Используйте числовые сноски:

```mdx
Утверждение подтверждается официальным источником.[^1]

[^1]: [Название источника](https://example.com).
```

Правила:

- Не используйте именованные сноски вроде `[^rfzo-law]`.
- Нумеруйте сноски в порядке появления.
- Ставьте сноску сразу после утверждения, которое она подтверждает.
- Ссылка должна вести на конкретную страницу или документ, а не на главную сайта, если доступен точный источник.
- Для законов указывайте название акта и релевантную статью, когда это возможно.
- Не вставляйте длинные цитаты, если достаточно точного пересказа.
- Проверяйте, что все ссылки на сноски имеют определения и наоборот.

## Внутренние ссылки

Правильно:

```mdx
[РВП и ПМЖ](/arrival/boravak/)
```

Неправильно:

```text
[[arrival:boravak|РВП и ПМЖ]]
arrival:boravak
../boravak/
```

Перед добавлением ссылки:

1. Проверьте файл в `src/content/docs`.
2. Проверьте маршрут в `CONTENT_INDEX.yml`.
3. Для ссылки на раздел проверьте фактический Astro heading ID.
4. Не создавайте ссылку на будущую или предполагаемую страницу.

При создании, удалении, переносе или переименовании страницы обновите `CONTENT_INDEX.yml`. Для переноса дополнительно проверьте `astro/public/_redirects` в `Antiokh/rslive.ru`.

## Markdown и MDX

Используйте стандартный Markdown:

```mdx
## Раздел

- пункт;
- пункт.

| Колонка | Значение |
| --- | --- |
| Пример | Данные |
```

Не используйте autolink в угловых скобках:

```mdx
<!-- Нельзя -->
<https://example.com>

<!-- Можно -->
[https://example.com](https://example.com)
```

Не оставляйте необработанный DokuWiki-синтаксис в статье. Архивный пример допустим только внутри fenced code block с пояснением.

## Компоненты

Компоненты автоимпортируются. Не добавляйте повторяющиеся импорты вида:

```mdx
import Aside from '@astrojs/starlight/components/Aside.astro';
```

Выбирайте компонент по смыслу:

- `Aside` — примечание, совет, осторожность или опасность;
- `Steps` — последовательность действий;
- `Accordion` + `AccordionItem` — несколько связанных раскрывающихся блоков;
- `Spoiler` — один необязательный скрываемый блок;
- `UplatnicaGenerator` — платёжная квитанция;
- `SmartTable` — статические или JSON/API-строки с фильтром и сортировкой;
- `StructTable` — известная схема данных из конфигурации основного приложения;
- `SupabaseTable` — таблица из Supabase;
- `SanityTable` — таблица из Sanity;
- `MapEmbed` — карта;
- `EmbedFrame` — другой iframe;
- `YouTube` — видео YouTube;
- `ContentInclude` — включение существующей страницы или раздела;
- `MermaidGraph` — Mermaid-диаграмма;
- `Countdown` — фиксированный или ежегодный счётчик даты.

Полный синтаксис см. в `docs/MDX_COMPONENTS.md`. Перед использованием редкого компонента проверьте его текущий исходник в `Antiokh/rslive.ru`.

## DokuWiki-миграция

Не удаляйте функциональность при миграции. Например:

- `<uplatnica ... />` преобразуйте в `UplatnicaGenerator`, а не в скриншот;
- `++++ ... | ... ++++` преобразуйте в `Spoiler` или `Accordion`;
- `<callout>` / `<alert>` преобразуйте в `Aside`;
- `{{section>...}}` / `{{page>...}}` преобразуйте в `ContentInclude` либо статически встроенный текст с указанием источника;
- `{{url>...}}` преобразуйте в `MapEmbed`, `YouTube` или `EmbedFrame` по типу URL;
- `((сноска))` преобразуйте в числовую Markdown-сноску;
- DokuWiki-таблицу преобразуйте в Markdown-таблицу или подходящий управляемый компонент.

Полная таблица находится в `docs/DOKUWIKI_MIGRATION.md`.

## Таблицы

Используйте обычную Markdown-таблицу, когда:

- строк мало;
- данные статичны;
- фильтрация и сортировка не нужны.

Используйте `SmartTable`, когда:

- строк много;
- нужна фильтрация или сортировка;
- есть длинный текст, ссылки или иконки;
- данные задаются массивом или JSON endpoint.

Используйте управляемые таблицы только после проверки источника данных и схемы в основном репозитории. Не копируйте динамическую таблицу вручную в MDX, если она уже поддерживается `StructTable`, `SupabaseTable` или `SanityTable`.

## Изображения, карты и медиа

- Добавляйте осмысленный alt-текст.
- Не используйте изображение вместо текста, таблицы или квитанции, если данные должны быть доступны поиску и ассистивным технологиям.
- Для iframe всегда задавайте `title`.
- Для карты используйте `MapEmbed`, для YouTube — `YouTube`, для остальных допустимых iframe — `EmbedFrame`.
- Не вставляйте произвольный `<iframe>` без проверки безопасности и необходимости.
- Не храните реальные персональные данные плательщика в props `UplatnicaGenerator`; текущая реализация передаёт QR payload внешнему сервису, что отдельно описано в `docs/MDX_COMPONENTS.md`.

## Изменения компонентов

Если задача требует нового компонента или изменения props существующего:

1. Вносите реализацию в `Antiokh/rslive.ru`.
2. Обновите `astro/astro.config.mjs`, если нужен автоимпорт.
3. Обновите `astro/CUSTOMIZATION_INVENTORY.md`.
4. Обновите `docs/MDX_COMPONENTS.md` в этом репозитории.
5. Не используйте новый синтаксис в контенте до появления реализации в основной ветке или согласованной связанной ветке.

## Проверка перед PR

Проверьте:

- [ ] изменены только относящиеся к задаче файлы;
- [ ] frontmatter корректен;
- [ ] `title` и `description` соответствуют содержанию;
- [ ] внутренние ссылки существуют;
- [ ] сноски числовые и полные;
- [ ] фактические и юридические утверждения подтверждены;
- [ ] старый DokuWiki-синтаксис удалён или показан только как код;
- [ ] MDX-компоненты существуют и props совпадают с `Antiokh/rslive.ru`;
- [ ] JSX/MDX-теги парные;
- [ ] `CONTENT_INDEX.yml` обновлён при изменении маршрутов или структуры;
- [ ] необходимость редиректа проверена;
- [ ] сборка запущена в основном репозитории либо ограничение явно указано.

## Git и PR

- Создавайте ветку `agent/<краткое-название>` от актуального `main`.
- По умолчанию открывайте draft PR.
- Не смешивайте редакционную переработку, массовую миграцию и несвязанные технические изменения.
- В PR укажите изменённые страницы, источники, проверки и ограничения.
- Не утверждайте, что сборка прошла, если она не запускалась в `Antiokh/rslive.ru/astro`.
